# 06 — الاختبارات ومعايير قبول أي تطوير

## نقطة الانطلاق العملية
استعمل نسخة محلية منعزلة وافحص `pyproject.toml` ثم:
```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e '.[test]'
python -m pytest -q
```
هذا مثال تشغيل محلي؛ يحتاج PyTorch مناسباً للبيئة، ولا ينبغي تشغيله مباشرة داخل الإنتاج.

## واجب التأكد قبل أي تغيير
- tests نجاحها برقم وتاريخ وSHA commit الحالي.
- API authorization لكل route، رفض الطلبات غير الموثقة.
- سلامة ملفات model and optimizer checkpoints ومطابقة dataset hashes.
- عدم تسرب بيانات holdout، عدم ظهور secrets في logs، عدم تنفيذ MD.
- CPU وGPU admission checks مع simulation (بدون تشغيل GPU).
- لا خسارة للبيانات أو انقطاع للخدمات بعد إعادة تشغيل مصرح بها.
- مقارنة ردود candidate وlegacy مع prompts غير مستخدمة أثناء التدريب.

## معيار محادثة حقيقي
لا يكفي `train_loss`. يجب أن تقاس: صحة الرد، ارتباطه بالسؤال، العربية والدارجة والإنجليزية، عدم الخلط بين الأدوار، طلب التوضيح، ذاكرة السياق القصير، وتكرار الإجابات عبر seeds مختلفة. ضع threshold واضحاً قبل قبول أي نسخة.

## ثغرات مؤكدة
1. لا Model Registry/Selector للنسخ مدمج في API للامتحان.
2. الموديل الحالي صغير والسياق 128 بايت-token للمرشح؛ لا قدرة حوارية مؤكدة.
3. لا اعتماد production-quality datasets متعدد اللغات.
4. التدريب الحسابي توقف عند التشبع، وليس بسبب إيقاف تلقائي لـGPU.
5. لا claim صحيح لـFSDP/multi-node أو multimodal الخاص بالأوزان.
6. ضمانات 24/7 واستعادة خارج RunPod بحاجة لاختبارات تشغيل واقعية.
7. وثائق `docs/STATUS.md` قديمة؛ اعتمد آخر evidence وأعد قياسه.

**لا تفترض نجاح 100 خطوة = نموذج يتحدث.**
